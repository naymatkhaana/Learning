01 / THE IDEA

Take good practices to the extreme.

Extreme Programming was developed by pushing recognized software-engineering practices, such as iterative development, to very high levels.

What is XP?

Extreme Programming, commonly called XP, is an agile software-development approach focused on rapid feedback, continuous improvement, customer involvement, simplicity, and high-quality code.


In XP, several new versions of a system may be developed by different programmers, integrated, and tested within a single day.

The XP Mindset

Instead of spending a long time designing and building everything before getting feedback, XP encourages teams to build small pieces, test them, integrate them, and learn continuously.

📝

Plan

Choose a small piece of valuable functionality.

💻

Build

Implement the smallest useful solution.

🧪

Test

Automatically verify that it works.

🔗

Integrate

Combine the work with the whole system.

🔄

Improve

Refactor and continuously make the system better.

02 / CORE PRACTICES

The four practices you must know.

These practices demonstrate how XP turns agile principles into concrete everyday development activities.

1. User Stories

A user story describes a scenario of use from the perspective of the system user.

01
Example — Online Shopping
As a customer, I want to add products to my shopping cart so that I can purchase them later.

The customer and developer discuss the story together. The story is then broken into smaller development tasks.


Story: Add product to cart Tasks: 1. Create "Add to Cart" button 2. Create cart object 3. Update item quantity 4. Calculate cart total

2. Refactoring

Refactoring means improving the internal structure of code without changing its external behavior.

02
Example
// Before function x(a, b) { let c = a + b; return c; } // After function calculateTotal(price, tax) { let total = price + tax; return total; }

The behavior remains the same, but the code becomes easier to understand and maintain.

3. Test-First Development

Write the automated test before writing the code that makes the test pass.

03
Example — Login
1. RED Write a test: login("ali", "1234") → should return true 2. GREEN Write the minimum code needed to pass the test. 3. REFACTOR Improve the code while keeping all tests passing.
🔴

Red

Write a failing test.

🟢

Green

Write code that passes.

🟣

Refactor

Improve the design.

4. Pair Programming

Two developers work together at one workstation on the same piece of code.

04
Example
Driver: writes the code.

Navigator: reviews the code, thinks about the next step, and identifies potential problems.

The developers regularly switch roles so both understand the code.

03 / TEAMWORK

Two minds. One codebase.

Pair programming is more than two people typing together. It creates continuous communication, review, knowledge sharing, and collective responsibility.

✓
Supports collective ownership and responsibility for the system.
✓
Acts as an informal review process because every line of code is examined by at least two people.
✓
Encourages developers to refactor and improve the structure of the software.
04 / XP PRINCIPLES

More principles and practices.

XP is not just about four practices. Its philosophy is supported by a broader set of principles and team behaviors.

Principle / Practice Description
Collective Ownership Developers work across all areas of the system. No islands of expertise should develop. Anyone can change anything.
Continuous Integration Completed tasks are integrated into the whole system as soon as possible. Automated tests must pass after integration.
Incremental Planning Requirements are recorded on story cards. Stories are prioritized based on business value and available development time, then divided into tasks.
On-Site Customer A representative of the end user is available to the team and helps clarify and prioritize requirements.
Pair Programming Developers work in pairs, checking each other's work and helping maintain high-quality code.
Refactoring Developers continuously improve the structure of code whenever opportunities for improvement are discovered.
Simple Design Do enough design to satisfy the current requirements, but avoid unnecessary complexity.
Small Releases Deliver the minimum useful functionality first, then release additional functionality frequently.
Sustainable Pace Excessive overtime is avoided because it can reduce code quality and long-term productivity.
Test-First Development Automated unit tests are written before implementing the corresponding functionality.

06 / REMEMBER

The XP philosophy in one slide.

⚡

Fast Feedback

Develop in small increments and get feedback quickly from tests, customers, and teammates.

🧠

Keep It Simple

Build only what is needed now and continuously improve the design through refactoring.

🤝

Work Together

Customers and developers collaborate closely, while developers share ownership of the code.

🧪

Test Everything

Automated tests provide rapid feedback and help prevent regressions.

🔄

Improve Continuously

Refactoring and continuous integration keep the system healthy as it evolves.

🌱

Sustainable Pace

Avoid excessive overtime. Long-term productivity depends on maintaining quality and a healthy development pace.
